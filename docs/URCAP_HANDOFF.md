# ROS / OnRobot URCap handoff — next lab workflow

Status: implemented and tested against a fake pendant/ROS driver. **Not yet
loaded, parsed, or physically validated on PolyScope.** The direct XML-RPC
bench adapter remains available as a fallback. This preparation does not close
physical acceptance issues #8, #10, #11, #13, or #14.

The arm stays under ROS External Control for arm moves. ROS finishes the move,
calls the documented `hand_back_control` service, and the pendant executes its
ordinary OnRobot **RG Grip** node. A short socket acknowledgement identifies
the completed phase and carries gripper width/grip status. ROS waits for the
next External Control node **and** reactivated arm controller before continuing.
The acknowledgement uses documented URScript sockets; it does not call the
undocumented OnRobot XML-RPC endpoint or access the serial bridge.

## First acceptance: stationary arm, empty jaws

Use the laptop Ethernet connection: laptop `192.168.56.1`, UR7e
`192.168.56.101`. Keep OnRobot ownership of Tool I/O, 24 V, its working tool
connector setup, and the External Control URCap. Do not launch raw RS485/socat,
the native bench adapter, or another gripper/arm command client concurrently.
The presence of the RS485 installer is not proof of an active serial client.

The first profile is **close 59 mm / open 70 mm / force 5 N**, with an empty
gripper, a clear workspace, and a supervising operator at the pendant. Set the
pendant speed to 10%. Open the jaws to 70 mm using the existing pendant controls
before starting. No arm movement is requested in this mode; both joint velocity
and position drift are monitored during every gripper handoff.

Create a new program named `ros_onrobot_handoff` in PolyScope. This is a robot
**program**, not a new URCap installation. Keep the existing program as a backup.
Turn off **Program loops forever**. Load `scripts/pendant_handoff.script` into a
**Script → File** node in **BeforeStart**. It defines the helper functions and
opens the status socket; do not send this helper by itself over port 30002.
OnRobot's installation preamble must be generated by the enabled URCap.

Build this exact main program tree (no Move nodes for the first check):

| Order | PolyScope node | Contents/settings |
|---|---|---|
| 1 | External Control | Laptop `192.168.56.1`; ROS owns the stationary arm. |
| 2 | Script → Line | `lab_handoff_begin(1)` |
| 3 | OnRobot → RG Grip | Detected RG2, 59 mm, 5 N; depth compensation off. |
| 4 | Script → Line | `lab_handoff_done(1)` |
| 5 | External Control | Same laptop; wait for the next ROS phase. |
| 6 | Script → Line | `lab_handoff_begin(2)` |
| 7 | OnRobot → RG Grip | Same RG2, 70 mm, 5 N; depth compensation off. |
| 8 | Script → Line | `lab_handoff_done(2)` |
| 9 | External Control | Same laptop; confirms ROS control has returned. |

Use **RG Grip**, not RG2-FT Grip. Verify both nodes wait for completion. The
exported 6.5.0 program used `blocking=True` for this node. The single RG2 in our
installation is tool index 2; the standard single-gripper feedback variables
`rg_Width`, `rg_Busy`, and `rg_Grip_detected` map to that device in its preamble.
The helper checks the index at startup. It is not a general dual-gripper program.

Review and save the installation/program before Play. The helper constants,
the two RG Grip node settings, and the ROS CLI settings must agree. The handshake
checks the helper's declared settings and initial width; it cannot introspect
the GUI nodes' actual force/width settings. Export and inspect the generated
script before physical acceptance. If script loading/compilation fails, stop
there and preserve the error instead of substituting a different command path.

In the configured lab ROS environment, source ROS and the workspace, run the
normal arm driver with `use_tool_communication:=false`, then run:

```sh
export ROS_DOMAIN_ID=42
python3 scripts/lab_urcap_handoff.py --execute-gripper --supervised
```

Wait for `awaiting_pendant_play`, then press Play on **ros_onrobot_handoff**.
The coordinator listens on laptop TCP **50010** and accepts only the configured
robot IP. It waits up to 120 seconds for Play. This is an additional status port,
separate from the External Control driver's reverse/script ports.

Expected sequence: External Control → authorized close → width confirmation →
External Control/controller active → authorized open → width confirmation →
External Control/controller active. Success is `handoff_sequence_complete`, two
phase records, widths within 1 mm, and no arm movement. The final External
Control node remains active and stationary; press **Stop** after recording the
result. Stop and restart the whole pendant program for a new run so BeforeStart
establishes a fresh session. Do not simply re-run the laptop client mid-program.

## Optional arm-position / grip / lift / release rehearsal

Only after stationary handoff, TCP/payload, combined collision model, and actual
named-pose validation have passed, run `motion_node` and supply **two already
validated names** through `--before-close-pose` and `--before-open-pose`, together
with `--validated-poses`. No physical poses are guessed or supplied by this change.

The first action moves to the chosen grasp pose, then hands off for close. The
second moves to the chosen lifted/release pose, then hands off for open. Each
`ExecutePrimitive` must return terminal `SUCCEEDED` and `success=true`; a failed
or uncertain action prevents the gripper phase. The controller must be active
and the arm settled at each handoff. Keep release over a suitable support and
verify the entire path, not only its endpoints. This two-pose rehearsal is not
the full ten-run pick/place acceptance sequence.

For a subsequent object trial, configure matching widths/force in the helper,
RG Grip nodes, and CLI (`--close-mm`, `--open-mm`, `--force-n`), and use
`--expect-object`. Closing then requires the URCap grip-detected flag and width
within the configured range; opening requires release and target width. Current
software bounds are 0–110 mm, <=20 mm between open/close, and 3–10 N. Grip
detection is not proof of sustained object retention, and measured force is not
available through this handshake. Nothing in this change authorizes unverified
TCPs, payloads, poses, or a first object trial without operator supervision.

OnRobot can change its active TCP/payload as part of tool selection. Verify those
settings against the ROS model before adding arm motions. Keep depth compensation
off initially: that option also moves the robot arm. The handshake itself
does not configure or validate the physical TCP/payload.

## Combined pick-and-place (one command)

`--pick-place` runs the **same step plan as the simulation demo**
(`scripts/pick_sequence.py`, also used by `scripts/pick_place_demo.py`), with
each gripper step replaced by a pendant handoff. The plan is split around the
two RG Grip phases of the pendant tree above:

| Segment | Arm motions (ROS, `ExecutePrimitive`) | Then |
|---|---|---|
| before close | `home` → approach above pick → descend | handoff phase 1: RG Grip close |
| before open | lift → approach above place → descend | handoff phase 2: RG Grip open |
| after open | retreat → `observe` → `home` | final External Control node, then Stop |

The plan's initial "open" is satisfied by the pendant's hello check that the
jaws start at the open width. There are **no default physical coordinates**:
the pick and place points must be measured (base_link, metres, top-down grasp)
and passed explicitly, with the same gates as the two-pose rehearsal above.

```sh
python3 scripts/lab_urcap_handoff.py --execute-gripper --supervised \
    --pick-place --validated-poses \
    --pick-xyz 0.45 -0.15 0.08 --place-xyz 0.45 0.20 0.08 --expect-object
```

(The numbers shown are the simulation placeholders, not lab measurements.)
Omit `--expect-object` for a first empty-jaw run of the full path. Every
motion must succeed before the next handoff; any failure stops the program
without a grip. To rehearse the identical sequence in simulation first, run
`python3 scripts/pick_place_demo.py` against tier 1 or 3.

## Failure behavior

- A fresh session nonce and ordered phase IDs reject stale/duplicate completions.
- The pendant blocks **before RG Grip** until ROS grants the matching phase, and
  blocks **after RG Grip** until ROS validates the width/grip result.
- Handback failure/timeout is not retried: a delayed service execution must not
  cause a second grip. Socket loss/timeouts halt at the pendant gate.
- ROS checks NORMAL safety, recent joint/speed data, no active arm trajectory,
  bounded speed, settled arm state, and expected External Control ownership.
- Failure closes the socket, attempts cancellation of an owned arm action, and
  requests Dashboard Stop. An unacknowledged stop is explicitly reported; the
  operator must stop at the pendant. The software handshake is not a safety-rated
  interlock, and a connection loss during a grip does not prove immediate jaw stop.
- No automatic Play, resend, unlock, recovery, or retry occurs. The existing
  safety monitor remains active; expected External Control handoffs are phase
  transitions, not protective-stop recovery.
